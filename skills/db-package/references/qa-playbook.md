# QA プレイブック — 穴の見つけ方と外部レビューの回し方

3 部作で「自力のテストでは出なかった欠陥」（恒久ロックアウト・Tx 開始時刻の時刻源・
票なし承認・定義の全消去など）を実際に検出した手法集。**green なテストと穴の不在は別物** —
種類の違う検査を重ねることが本質。

## 1. FAQ 駆動 QA（仕様の沈黙を探す）

FAQ は読者への親切のためでなく、**答えに詰まる質問を探すため**に書く。

1. 外部 AI に仕様書（HANDOFF）を精読させ、読者ロール（組み込む開発者 / 各業務アクター /
   監査 / 運用 / 定義設計者）になりきった「質問だけ」を 50 問前後生成させる
2. 各質問を分類: [A] 現仕様で回答可能 / [B] 後工程で決まる予定 / [C] 穴（沈黙・矛盾・未検討）
3. [C] のうちエンティティ設計に効くものは**実装前に**発注者決定 → ADR。残りは実装後の
   FAQ 回答時に消化する
4. 回答を書くときは**必ず実装と突き合わせて**から収録し、「曖昧だった / 事実に反していた」
   回答を件数つきで列挙・対応する（回答の検証こそが第 2 の穴検出になる）

## 2. 探針シナリオ QA（実装の縁を突く）

実装完了後、デモとテストが踏まない縁を狙った使い捨てシナリオを実 DB で実行する。
結果は表（探針 → 観察 → 判定 → 処置）で docs/research/ に記録。

**「実 DB」= 使い捨ての開発用 DB（`make up` で立てた Docker の PostgreSQL）のこと。**
探針は恒久ロックアウトや定義の全消去を意図的に起こすので、共有 DB・ステージング・本番に
対して実行してはならない。並行テスト・デモ・bench も同じ。実行前に必ず:

- 接続先を確認する（`select current_database(), inet_server_addr(), inet_server_port()`
  と接続文字列の出所を記録に残す）。ローカルの Docker コンテナ以外なら中止して発注者に確認
- fixture は公開 SP で合成した使い捨てデータのみ。実データのコピーを持ち込まない
- 探針で壊した状態は `make down && make up`（または DB 再作成）で捨てる。ロールバックで
  戻せる前提を置かない（探針は COMMIT を伴うため）

狙いどころの型（3 部作で実際に穴が出た場所）:
- **管理系の自己破壊**: 最後の管理者を自分で剥奪 / 唯一の定義を消す — 恒久ロックアウト経路
- **境界値の定義**: 負値・ゼロ・int 上限・空文字・空配列・NULL を「定義できてしまうか」
  （定義できた場合に実行系がどう振る舞うか）
- **時間**: 長時間トランザクション・期限とバッチの同時刻・時計の前提（now() は Tx 開始時刻!）
- **ライフサイクルの跨ぎ**: 廃止後の進行中データ・版切替直後の操作・終端状態への全操作
- **フィルタ・引数の黙った空振り**: 不正な列挙値やタイポが「0 件」に見えないか
- **順序と重複**: 同一 ID の重複指定・到着順依存・並行コミットでの ID 逆転

## 3. 外部 AI レビュー（分割と方向が命）

- **一括依頼はしない**。コンテキストで破綻する（usedcar で実証）。
  「観点 × 対象」で 3〜5 系統に分割し、各系統に読むファイルを明示して依頼する
- 依頼文には必ず: 読み取り専用の明言 / 仕様の正の所在 / 出力形式
  （番号 + 重大度 + ファイル:行 + 内容 + 根拠。指摘ゼロの観点は「問題なし」と明記）
- 実装後は**方向別の敵対的レビュー**を行う。通常レビューと重複しない指摘が出る:
  1. **ADR → 実装**: 各 ADR の決定を箇条書きに分解し、実装箇所をトレース（宣言の適用漏れを数える）
  2. **実装 → 仕様**: コードにあるが仕様書のどこにも無い挙動・暗黙の既定値・エラー順序を炙り出す
  3. **テスト固定検査**: ADR の主張のうち、回帰しても誰も気づかないもの（テストに固定されて
     いない約束）を列挙させる
- レビュアのモデル・分割・件数は記録に残す（再現性と検収のため）

## 4. 指摘の処置 — 4 分類で全件記録

docs/research/external-review-*.md に全指摘の採否表を残す。分類は 4 つだけ:

| 分類 | 使いどころ |
|---|---|
| **修正** | 実装・スキーマを直した（回帰テストを必ず添える） |
| **文書化** | 実装は正しいが仕様書が沈黙 / 誤っていた → 文書を直す |
| **テスト追加** | 実装も文書も正しいが固定されていなかった |
| **明示受容** | 直さない。**理由を書く**（受容理由が無いと同じ指摘が次の巡で再来する） |

仕様の意味論に触れる修正は ADR 化し、発注者承認を明示的に取る（承認日を ADR に記録）。

## 5. 巡の設計（目安）

- 実装前: 敵対的レビュー（仕様の穴）+ FAQ 質問バンク + UC 突合
- 実装後: 観点×対象の分割レビュー（正しさ / 同時実行・冪等 / セキュリティ / 成果物整合）
- 仕上げ後: 探針 QA + FAQ 拡充 + 方向別敵対的レビュー（ADR 監査）
- 各巡の後は**その工程で実行可能なゲート**を全部再実行 → 1 巡 = 1 コミット
  - 実装前の巡: 文書 validate + スコープ QA の出口条件（FAQ 分類・ADR ブロッカーゼロ）のみ
  - 実装後の巡: 上に加えて test（pgTAP + 並行）
  - 仕上げ後の巡: 上に加えて demo（期待出力一致）+ bench（性能目標）
  実装前に demo / bench を「代替手段で通したことにする」のは禁止。存在しないゲートは
  記録に「該当工程未到達」と書く
